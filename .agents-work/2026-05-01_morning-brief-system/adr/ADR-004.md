# ADR-004 — Authentication and Secret Handling

**Date:** 2026-05-01  
**Status:** Accepted

---

## Context

Two of the five data sources (JIRA and NewsAPI) require API credentials. Three (Open-Meteo, MLB Stats API, Scryfall) require no authentication. The system runs unattended on GitHub Actions; credentials must not appear in source code, workflow YAML, logs, or generated reports. A clear, auditable mechanism for supplying and validating secrets is required.

---

## Decision

**Read all secrets from environment variables** using `os.environ.get()`. Validate required secrets at script startup before any API calls are made. Log the names of missing secrets (not their values) and exit with code `1` if any required secret is absent.

GitHub Actions workflow YAML maps repository Secrets to environment variables using the `env:` block — this is the canonical CI/CD pattern and keeps credential management entirely within GitHub's encrypted secret store.

---

## Alternatives Considered

| Option | Pros | Cons |
|---|---|---|
| **Environment variables from GitHub Secrets** (chosen) | Native CI/CD pattern, zero secret exposure in repo, automatic log masking | Requires admin to set secrets before first run |
| **`.env` file in repo** | Easy local dev | Secrets in source control — severe security violation |
| **Config file (e.g., `config.yaml`)** | Flexible | Values in repo or filesystem — security risk; not suitable for CI |
| **`python-dotenv` library** | Cleaner local dev | Extra dependency; not needed on CI; `.env` still risks accidental commit |
| **GitHub Actions OIDC / Vault** | Zero static secrets | Excessive complexity for this use case; JIRA/NewsAPI don't support OIDC |

---

## Consequences

- **Startup validation**: `validate_config()` in `morning_brief.py` checks all required env vars on startup. Missing secrets are logged by name only (e.g., `"Required secret JIRA_API_TOKEN is not set"`). If any required secret is missing, the script calls `sys.exit(1)` before any network calls.
- **GitHub Actions log masking**: The Actions runner automatically replaces secret values with `***` in workflow logs, providing a second layer of protection.
- **No secret persistence**: Secrets flow only through env vars during the runner's lifetime — they are never written to files, included in report output, or echoed in log lines.
- **Optional secret**: `OPENWEATHER_API_KEY` is not required; its absence does not trigger startup failure — `weather_fetcher.py` uses Open-Meteo instead.
- **Developer onboarding**: Repository administrators must manually add three secrets (`JIRA_API_TOKEN`, `JIRA_HOST`, `NEWSAPI_KEY`) in GitHub → Settings → Secrets before the first scheduled run.

---

## Notes

- Required secrets: `JIRA_API_TOKEN`, `JIRA_HOST`, `NEWSAPI_KEY`.
- Optional secrets: `OPENWEATHER_API_KEY` (enables OpenWeatherMap fallback).
- Workflow env block pattern:
  ```yaml
  env:
    JIRA_API_TOKEN: ${{ secrets.JIRA_API_TOKEN }}
    JIRA_HOST: ${{ secrets.JIRA_HOST }}
    NEWSAPI_KEY: ${{ secrets.NEWSAPI_KEY }}
    OPENWEATHER_API_KEY: ${{ secrets.OPENWEATHER_API_KEY }}
  ```
- `http_client.get` never logs request headers (which carry Bearer tokens); only URL (sans query params) is logged at DEBUG level.
- JIRA uses `Authorization: Bearer {JIRA_API_TOKEN}` header. NewsAPI uses `X-Api-Key: {NEWSAPI_KEY}` header. Neither value is interpolated into any log message or report section.
