# ADR-005 — Slack Notification Integration

## Context
After initial design approval, the user requested that a Slack notification be sent when the morning brief report is successfully generated. The notification should provide a quick summary without requiring users to open the file manually.

## Decision
Use Slack Incoming Webhooks via a simple HTTP POST using the `requests` library (already a project dependency). The notification is **optional**: if the `SLACK_WEBHOOK_URL` environment variable is not set, the notification step is silently skipped. This avoids making Slack a hard dependency for teams that do not use it.

## Notification Message Format
- Report filename (e.g., `Morning-Brief-2026-05-01.md`)
- Generation timestamp in ISO-8601 UTC format
- Per-source status indicators (✅ success / ❌ failed) for all 5 data sources

## Alternatives Considered
- **Slack SDK (slack-sdk library)**: Full-featured but adds a dependency. Overkill for a single webhook POST.
- **GitHub Actions-native notification (actions/slack-notify)**: Ties notification to workflow YAML instead of Python script; less testable and less portable.
- **Email notification**: Requires SMTP configuration; more complex; not requested.
- **No notification**: Rejected — user explicitly requested Slack notification.

## Consequences
- Adds one new optional GitHub Secret: `SLACK_WEBHOOK_URL`.
- Adds one new module: `scripts/notifiers/slack_notifier.py` (~30 lines).
- Zero impact if `SLACK_WEBHOOK_URL` is not configured (graceful skip).
- Notification failure is non-fatal — does not affect report delivery or workflow exit code.
- Slack message content never includes API keys or secret values.

## Notes
Incoming Webhooks are the simplest Slack integration pattern. The webhook URL itself is the credential — store it as a GitHub Secret. HTTPS POST to `https://hooks.slack.com/services/...` with a JSON payload `{"text": "..."}`.
