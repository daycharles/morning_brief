# ADR-003 — Execution Model: Synchronous vs Parallel / Async

**Date:** 2026-05-01  
**Status:** Accepted

---

## Context

The script must call five independent external APIs and complete within 5 minutes (NFR-001). Each HTTP call has a 10-second timeout and up to 2 retries (max ~30 seconds per fetcher in the worst case). Sequentially, worst-case total time is ~150 seconds (5 × 30s). Parallel execution reduces this to ~30 seconds (bounded by the single slowest fetch). A choice must be made between sequential execution, thread-based concurrency, async I/O, or multiprocessing.

---

## Decision

**Use `concurrent.futures.ThreadPoolExecutor`** from the Python standard library with `max_workers=5` to execute all five fetcher functions concurrently.

Each fetcher is submitted as a `Future`. The orchestrator calls `future.result()` for each with a per-future timeout guard. Exceptions inside any fetcher are caught internally by the fetcher itself and returned as a failed `FetchResult`, so `Future.result()` always yields a `FetchResult` without raising.

---

## Alternatives Considered

| Option | Pros | Cons |
|---|---|---|
| **ThreadPoolExecutor** (chosen) | stdlib, simple API, handles I/O-bound tasks, familiar to all Python devs | GIL applies (not an issue for I/O-bound work) |
| **asyncio + aiohttp** | True async, efficient I/O | External dependency (`aiohttp`); more complex code; async-all-the-way-down refactoring burden |
| **Sequential execution** | Simplest code | Worst-case ~150s; cannot meet 5-minute SLA under retry pressure; unacceptable |
| **multiprocessing.Pool** | True parallelism | High overhead for 5 lightweight I/O tasks; inter-process serialization complexity |
| **Celery / task queue** | Scalable | Massive over-engineering for a single daily script on a single runner |

---

## Consequences

- **Total execution time** bounded by the single slowest fetcher (max ~30s with retries), well within the 5-minute SLA.
- **Zero external async dependencies**: only `requests` (sync) and stdlib `concurrent.futures` are needed.
- **Exception isolation**: each fetcher's internal `try/except` ensures a failure in one thread never propagates to the `ThreadPoolExecutor` dispatch loop.
- **Deterministic ordering**: results are collected after all futures complete; report section order is fixed by the orchestrator, not by completion order.
- **Thread count**: fixed at 5 (one per fetcher); no dynamic scaling needed.

---

## Notes

- Pattern used in `morning_brief.py`:
  ```python
  from concurrent.futures import ThreadPoolExecutor, as_completed

  fetchers = [jira_fetch, weather_fetch, news_fetch, sports_fetch, mtg_fetch]
  with ThreadPoolExecutor(max_workers=5) as executor:
      futures = {executor.submit(fn, config): fn.__name__ for fn in fetchers}
      results = {name: future.result() for future, name in futures.items()}
  ```
- `requests` is thread-safe for concurrent use across independent sessions.
- If the GitHub Actions runner imposes a job timeout before 5 minutes, the workflow will be cancelled; the partial file may exist on disk (EC-007 is accepted).
